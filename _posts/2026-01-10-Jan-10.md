### Leetcode 2629 - [Function Composition](https://leetcode.com/problems/function-composition/)

#### 2629 Prompt
>
>"Given an array of functions `[f1, f2, f3, ..., fn]`, return a new function `fn` that is the **function composition** of the array of functions.
>
 > The **function composition** of `[f(x), g(x), h(x)]` is `fn(x) = f(g(h(x)))`.
 >
> The **function composition** of an empty list of functions is the **identity function** `f(x) = x`.
>
> You may assume each function in the array accepts one integer as input and returns one integer as output."

#### 2629 Solution

```js
/**
 * @param {Function[]} functions
 * @return {Function}
 */
var compose = function(functions) {
    return function(x) {
        for (const fn of functions.reverse()) {
            x = fn(x)    
        }
        return x;
    }
};
```

## Git Notes

### Commit Messages

#### General

Commits are "snapshots" of your code at the moment the commit was made. It's best practice to commit every time you have made a meaningful change in the code. This creates a timeline of your code, showing that the finished code did not appear out of nowhere and it makes bug-fixing easier to find with more stages saved instead of fewer.

It's important to write good commit messages so anyone reading your code and the commits (including other developers and future you) can easily understand what changes were made and why.

### Anatomy of a Commit Message

Commit messages have two parts - the subject and body. A GitHub commit message subject has a 72-character limit. The body can be longer.

The subject should be a brief summary of the change you made to the project.

The body should be a concise and clear description of what you did. Describing the problem you commit solves and how.

Read: [[Clippings/How to Write a Git Commit Message|How to Write a Git Commit Message]]

#### Anatomy Article Notes

- Sometimes commit messages for the same project can range from being long and clear and short and vague. it's a better use of energy, intention and better for future reviewers for the commit messages to be consistent in style and clarity - err on the medium side using concise.
- "Commit message shows whether a developer is a good collaborator." - [Peter Hutterer](https://who-t.blogspot.com/2009/12/on-commit-messages.html)
- It's common for a developer that doesn't use `git log` often to not think to much about the history of commit messages. Messages can remain unstructured and inconsistent without review.
- "A project’s long-term success rests (among other things) on its maintainability, and a maintainer has few tools more powerful than his project’s log. It’s worth taking the time to learn how to care for one properly. What may be a hassle at first soon becomes habit, and eventually a source of pride and productivity for all involved."
- Teams should all agree on commit message convention that defines three things:
  - Style: Markup syntax, grammar, etc. This makes a log consistent and makes reading it required and pleasant.
  - Content: The information that the body of a message should and should not contain.
  - Metadata: How should numbers and IDs be referenced
- Seven Rules of a great Git commit message
  1. Separate the subject from the body with a blank line
  - Not every commit requires both a subject and a body. When a reader can understandably require more context, a body is required.
  - Commit messages with bodies are not easily written on the CLI - use a text editor.
  - Separating makes parsing through the log easier
  - `git log --oneline` prints out just the subject line
  - `git shortlog` prints commit subject lines grouped by user
  1. Limit the subject line to 50 characters
  - There is a 72-character hard limit, 50 is best practice.
  1. Capitalize the subject line
  2. Do not end the subject line with a period
  3. Use the imperative mood in the subject line
      - Imperative mood means something is written as if giving a command or instruction as opposed to *indicative mood*, which is about reporting facts.
  - **All properly formed Git commit subject lines should be able to complete the following sentence: "If applied, this commit will -your subject line here-"**
  1. Wrap the body at 72 characters
  - Git does not wrap text automatically, you must mind the right margin and wrap text manually at 72 characters per line
  1. Use the body to explain what and why and not how
  - Let the code explain how the change was made and use the body to explain why the change was made, the way things worked before, the way they work now, and why you decided to solve it the way you did.

##### Key takeaways

- **Use the imperative mood in the subject line of commit messages, as if giving a commend or instruction**
  - This follows the Git convention of statements and events being written as if giving a command, "Update getting started documentation", "Refactor subsystem X for readability", "Release version 1.0.0"

### Atomic Commits

Commits should also be atomic, resolving around one task or one fix. These commits separate different fixes into separate commits. They should only be committed when a block of work is complete.

Read: [[Developer Tip Keep Your Commits "Atomic"]]

#### Atomic Article Notes

- "The ability to share code with multiple developers, track changes, and easily roll back when problems arise is indispensable"
- An "atomic" commit is about one task or one fix.
- **If given the task to change something in the layout and fix a bug, it is best practice to fix the bug as one change, and the layout changes as a separate fix. That way if you need to roll back the bug fix it won't undo the layout change. It can even be wise to commit each layout change separately so that they are not all tied to one commit.**
- It can be beneficial to atomize your commits especially when working on multiple files so that if you roll back changes you only have one file's changes to contend with and not a bunch of them (layout file, code behind the file, resource files, etc)

##### Key take away

- It's best to make your commits atomic so that if you have to roll back for a fix or problem it does not impact another aspect - this makes your project flexible for bug fixes, feature migrations and rollbacks

### Tips

- Commit early and often!
- Use an active voice: "Fix card generator"
- Avoid vague language "saved" or "updated"
